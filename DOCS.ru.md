## Мастер настройки — полное описание шагов

И при первом добавлении интеграции, и в **Настроить** на карточке интеграции (`OptionsFlow`) сначала показывается меню:

- **Настроить по шагам** — обычный пошаговый мастер, описанный ниже;
- **Импортировать экспортированную конфигурацию** — доступно и при первом добавлении, и в `OptionsFlow`;
- **Экспортировать текущую конфигурацию** — только в `OptionsFlow`, см. раздел «Экспорт и импорт конфигурации» ниже.

**Шаг 1. Выбор вентиляторов.** Мультивыбор сущностей `fan` для притока и для вытяжки.

**Шаги на каждый вентилятор (по кругу, сначала приток, потом вытяжка):**

1. *Тип управления*: **дискретные ступени** (preset modes) или **плавный процент** (0-100 %). Здесь же — чекбокс **«Только чтение (автономный вентилятор)»**.
2. *Производительность*:
   - ступени: расход в м³/ч на каждую ступень через запятую, начиная со ступени 0 (например `0,30,45,60,75,90,140`);
   - процент: максимальный расход в м³/ч при 100 %.

   Здесь же задаются **дневной** и **ночной потолок** — максимальная ступень или процент вне и во время тихих часов соответственно. Пусто означает без ограничения; если тихие часы не настроены глобально (см. ниже), действует только дневной потолок.
3. *Правила по датчикам* (можно добавлять сколько угодно; пустое поле датчика завершает ввод). Для вентилятора «только чтение» этот шаг и оба потолка пропускаются — им всё равно некому следовать.

**Финальный шаг. Глобальные параметры:**

- бинарный датчик присутствия (необязательно);
- минимумы «дома / не дома» отдельно для ступенчатых (в ступенях) и процентных (в %) вентиляторов;
- два `input_datetime` с границами ночи (задаются оба или ни одного);
- интервал отправки команд на железо, в секундах (5-3600);
- **допуск по давлению** (м³/ч) и **максимальное время коррекции** (с) — см. раздел «Защита от затяжного дисбаланса» ниже.

Изменить всё это на лету можно через **Настроить** на карточке интеграции (`OptionsFlow`) → **Настроить по шагам**. Мастер повторяется с сохранёнными значениями, существующие правила остаются (можно отметить «Сначала удалить сохранённые правила»). После сохранения интеграция перезагружается.

## Экспорт и импорт конфигурации

В `OptionsFlow` (**Настроить** на карточке интеграции) пункт меню **«Экспортировать текущую конфигурацию»** показывает всю текущую конфигурацию (все вентиляторы, профили, правила, глобальные параметры) одним JSON-объектом в текстовом поле — выделите и скопируйте его. Отправка этой формы ничего не меняет в интеграции, это просмотр.

Этот же JSON можно вставить обратно через **«Импортировать экспортированную конфигурацию»** — она доступна и в меню `OptionsFlow` (заменяет текущую конфигурацию целиком), и в меню при первом добавлении интеграции (например, чтобы быстро перенести настройки на другой экземпляр Home Assistant или после переустановки). Перед принятием конфигурация проходит ту же проверку, что и обычный пошаговый мастер (карты расходов, правила, диапазоны глобальных параметров) — при ошибке форма показывается снова с описанием конкретной проблемы. Ссылки на сущности (вентиляторы, датчики) при импорте не проверяются на существование в этом экземпляре HA — так же, как и при обычном вводе через мастер; это позволяет, например, подготовить конфигурацию заранее.

## Правила по датчикам

Каждое правило превращает состояние датчика в **требуемый уровень** вентилятора: номер ступени или процент, в зависимости от типа управления. Если сработало несколько правил, берётся максимум.

| Режим | Когда срабатывает |
|---|---|
| `above` | число > порога |
| `below` | число < порога |
| `on` / `off` | бинарный датчик включён / выключен |
| `linear` | число ≥ порога; выход линейно растёт от «уровня на пороге» до значения выхода на верхнем пороге |

Для недоступных (`unavailable` / `unknown`) датчиков в каждом правиле задаётся политика: **inactive** (нейтрально, правило не срабатывает) или **active** (безопасный режим, правило срабатывает со своим выходом).

### Порог как значение другого датчика

Порог (`threshold`) и верхний порог линейного режима (`threshold_high`) не обязаны быть фиксированным числом. В форме правила есть два параллельных поля — число и датчик:

- **Threshold** / **Threshold sensor** — для нижнего порога;
- **Upper threshold** / **Upper threshold sensor** — для верхнего порога (линейный режим).

Если выбран датчик, **он всегда имеет приоритет** над введённым числом для той же границы. Типичный пример — сравнение не с фиксированными 40 % влажности, а с показаниями виртуального `sensor.average_humidity`, который сам усредняет несколько комнат. Датчик порога может быть `sensor`, `input_number` или `number` — то есть любым источником числового значения, включая `template`-сенсоры и `input_number` из UI Home Assistant.

Контур 1 отслеживает такие датчики-пороги точно так же, как и обычные датчики правил: изменение значения `sensor.average_humidity` сразу вызывает пересчёт.

Если датчик-порог становится `unavailable`/`unknown`, применяется та же политика `on_unavailable`, что и для основного датчика правила (неактивно или безопасный выход) — отдельно настраивать её для порога не нужно.

### Задержка активации (антидребезг)

У каждого правила есть необязательное поле **«Задержка активации (антидребезг), с»**. Пока «сырое» активно/неактивно состояние правила не продержится без изменений дольше этого времени, правило не влияет на спрос вентилятора — срабатывает классический дебаунс: любой кратковременный возврат в прежнее состояние сбрасывает отсчёт заново, а не накапливается. Значение по умолчанию — 0 (мгновенно, прежнее поведение). Полезно, например, для датчика присутствия, который может мигнуть на долю секунды, или для датчика влажности с шумными показаниями. Как только задержка истекла и правило подтверждено активным, сама величина выхода (для линейного режима) продолжает свободно следить за живым значением датчика — задержка относится только к самому решению «включать/выключать», а не к непрерывному выходу.

### Гистерезис (зазор включения) — почему вентилятор может «дёргаться» у порога

Если сырое значение датчика (особенно когда порог сам динамический, например вычисляется отдельным сенсором средних величин по нескольким комнатам) подолгу «висит» около порога, оно почти неизбежно колеблется вокруг него на доли процента — из-за шума датчика, работы самого вентилятора, конвекции воздуха, или дрожания самого вычисляемого среднего. Без зазора между точками включения и выключения правило **мигает** активно/неактивно при каждом таком микроколебании: неактивное состояние сразу роняет спрос до минимума (`floor`), активное — поднимает обратно, и это видно как вентилятор, который «то увеличивает, то уменьшает» скорость — причём не только у «своего» вентилятора, а у всей группы, поскольку изменение цели у одного вытяжного вентилятора через механизм поддержания баланса (см. «Математика баланса» ниже) подтягивает и приточные.

Поле **«Гистерезис (зазор включения)»** (только для режимов `above`/`below`/`linear`) решает это: активировавшись, правило не гаснет при первом же обратном пересечении порога, а остаётся активным, пока значение не отойдёт от порога на заданную величину **в сторону деактивации**. Активация при этом по-прежнему происходит ровно на пороге — зазор односторонний, как в обычном термостате. Пока значение находится внутри этого зазора (уже было активно, но чуть ниже номинального порога), линейный выход фиксируется на `output_low`, а не уходит в отрицательные значения.

Гистерезис и задержка активации решают разные по природе проблемы и хорошо работают вместе: гистерезис — это зазор **по значению**, задержка — зазор **по времени**. Если источником нестабильности служит именно дрожание промежуточного усредняющего сенсора (`sensor.average_humidity` и подобные), стоит также увеличить окно усреднения или сглаживание у самого этого сенсора — гистерезис в правиле смягчает последствия, но не заменяет сглаживание на источнике, если оно отсутствует.

## Два контура исполнения

**Контур 1: мгновенный расчёт (по событиям).** Через `async_track_state_change_event` отслеживаются все датчики правил, вентиляторы, датчик присутствия и `input_datetime`. При любом изменении сразу пересчитываются цели и обновляются атрибуты мастер-сущности. **Команды на вентиляторы не отправляются.**

**Контур 2: троттлинг исполнения (по таймеру).** Через `async_track_time_interval` с заданным интервалом контроллер:

1. пересчитывает цели (чтобы учесть смену дня/ночи по времени);
2. сравнивает текущее состояние вентиляторов с целями;
3. применяет **плавный ход**: не более ±1 ступени или ±5 % за тик;
4. отправляет `fan.set_preset_mode`, `fan.set_percentage` или `fan.turn_off`.

Порядок команд в тике сохраняет избыточное давление: сначала увеличение притока и уменьшение вытяжки, затем остальное.

Соответствие ступеней и режимов: если у вентилятора число `preset_modes` равно числу ступеней без нулевой, ступень *N* соответствует `preset_modes[N-1]`, ступень 0 это `turn_off`. Иначе ступень переводится в процент (`N * 100 / число ступеней`).

## Вентиляторы «только чтение»

Вентилятор можно пометить как **автономный** (read-only) — например, если им управляет собственная логика устройства или сторонняя автоматизация. Для такого вентилятора:

- балансировщик **никогда не отправляет ему команды** — ни в обычном режиме, ни при принудительной коррекции;
- его текущая реальная производительность (расход, вычисленный из фактического состояния) **учитывается в общем балансе** наравне с управляемыми вентиляторами — остальные вентиляторы той же роли подстраиваются вокруг него;
- в расчётах его цель всегда равна его же текущему фактическому уровню (floor = ceiling = demand = факт) — поэтому он никогда не попадает в списки «поднять»/«понизить»/«подрезать» на этапах балансировки;
- шаги мастера «Дневной/ночной потолок» и «Правила по датчикам» для него пропускаются — управлять нечем;
- если его состояние недоступно, он исключается из баланса как и любой другой недоступный вентилятор (его расход считается нулевым).

## Защита от затяжного и от избыточного дисбаланса

Основная цель балансировщика — держать приток и вытяжку на уровне примерно ±0 друг к другу, с небольшим допустимым перевесом притока над вытяжкой (но не наоборот). Независимые вентиляторы физически разгоняются с разной скоростью (ступени — по 1 за тик, проценты — по 5 % за тик, да ещё и нелинейно по карте расхода), поэтому даже при идеально рассчитанной цели простой независимый плавный ход каждой стороны может на несколько минут развести фактический приток и фактическую вытяжку в любую сторону. Чтобы этого не происходило, исполнение вытяжных вентиляторов **синхронизировано с фактическим текущим притоком**, а не только со своей конечной целью.

### Темп вытяжки привязан к фактическому притоку

На каждом тике, перед тем как решать, что делать с вытяжными вентиляторами, контроллер строит коридор `[фактический_приток − допуск, фактический_приток + допуск]` (допуск — `pressure_tolerance`, по умолчанию 15 м³/ч) и сжимает в него **суммарный** целевой расход всех вытяжных вентиляторов — если конечная цель выше коридора, она обрезается сверху; если ниже — поднимается снизу. Если вытяжных вентиляторов несколько, итоговая поправка распределяется между ними пропорционально их собственным целям. Полученное значение (`goal_level`) становится ориентиром для вытяжки на этот тик — именно к нему, а не к конечной цели, идёт обычный плавный ход (±5 %/±1 ступень за тик).

Это работает симметрично в обе стороны:
- **Вытяжка выше притока** (например, резко сработал датчик присутствия и поднял спрос до 100 %, а приток ещё только начал разгоняться со ступени 2) — коридор не даст вытяжке прыгнуть к далёкой конечной цели, пока приток её физически не нагонит; вытяжка будет подтягиваться вверх **вслед за фактическим** притоком, на каждом тике пересчитывая коридор заново, и доберётся до истинной цели только тогда, когда это сделает и приток.
- **Вытяжка ниже притока** (приток ещё не успел снизиться до своей новой, более низкой цели) — коридор не даст вытяжке обрушиться далеко вниз, обгоняя приток, и тем самым не создаст обратный, положительный перекос вместо устранённого отрицательного.

### Немедленная коррекция при выходе за допуск

Обычный плавный ход достаточен, пока коридор и фактические значения не разошлись заметно. Но если **фактическая** разница между притоком и вытяжкой уже превышает `pressure_tolerance` по модулю — вытяжные вентиляторы в этом же тике переводятся прямо на `goal_level` (уже ограниченный тем же коридором, см. выше), минуя обычный плавный шаг, вместо того чтобы несколько тиков ползти к нему по ±5 %. Поскольку целью служит всегда `goal_level`, а не сырая конечная цель, это никогда не создаёт перелёт в противоположную сторону — только убирает лишнюю задержку. Событие пишется в лог уровнем `WARNING`.

### Вотчдог «зависших» вентиляторов

Независимо от давления, контроллер отслеживает **фактический** уровень каждого управляемого вентилятора между тиками и сравнивает его с **текущим ориентиром** (`goal_level`) — для вытяжки это уже скорректированное коридором значение, а не далёкая конечная цель, иначе само по себе намеренное отставание вытяжки от цели (см. выше) выглядело бы как зависание. Если уровень **не меняется вообще**, пока он всё ещё заметно отличается от ориентира, засекается время. Вентилятор, который действительно постепенно движется (даже если ему требуется много тиков из-за большого исходного разрыва), таймер никогда не остановит — он сбрасывается при любом реальном изменении уровня. Но если фактический уровень застыл на месте дольше **максимального времени коррекции** (`max_correction_seconds`, по умолчанию 180 с) — вентилятор принудительно переводится прямо на текущий ориентир (`goal_level`), в обход плавного хода, с предупреждением в лог.

Это защищает от сценария, когда что-то (несовпадение количества `preset_modes`, задержка отклика устройства, пропущенное событие состояния и т. п.) молча блокирует обычные пошаговые команды: без этого вентилятор мог бы часами оставаться на старом уровне несмотря на совсем другую цель; теперь расхождение гарантированно устраняется не позже чем через `max_correction_seconds` — и, благодаря использованию `goal_level`, устраняется без риска перегнать противоположную сторону.

Оба механизма видны в атрибутах мастер-сущности и сенсоров целевого расхода: `stuck_seconds` — сколько секунд вентилятор уже «застрял» (`null`, если он сходится нормально).

## Математика баланса

1. **Спрос каждого вентилятора** = `max(минимум по присутствию, правила)`, не выше ночного потолка.
2. **Расход**: ступени берутся из карты расходов; процент считается как `Current_Airflow = (Current_Percentage / 100) * Max_Airflow_Capacity`.
3. **Избыточное давление.** Пока суммарный приток меньше суммарной вытяжки, приточные вентиляторы поднимаются по одному шагу (+1 ступень или +5 %) в пределах потолков; поднимается наименее загруженный.
4. **Защита.** Если приток упёрся в потолки, вытяжка уменьшается до притока. В атрибутах появляется пометка `exhaust_throttled_for_positive_pressure`.
5. **Паритет.** Вытяжные вентиляторы подстраиваются под текущий приток: сначала крупные ступени, которые ещё помещаются в остаток, затем плавные процентные вентиляторы для точной доводки.
6. **Подрезка.** Излишек притока сверх собственного спроса срезается, если это не нарушает условие «приток ≥ вытяжка».

Целевая дельта `target_delta_m3h` стремится к 0. Точный ноль достижим, когда есть хотя бы один процентный вентилятор в нужной роли. При одних дискретных ступенях остаётся неизбежная остаточная дельта, а положительное давление всегда приоритетнее (`delta ≥ 0`). Если минимумы или правила притока превышают возможности вытяжки, дельта остаётся положительной и появляется пометка `residual_positive_delta`.

## Отказоустойчивость

- Недоступный вентилятор исключается из баланса (его расход считается нулевым), остальные продолжают работать; вытяжка при этом ограничивается фактическим притоком.
- Недоступный датчик заменяется политикой из правила; та же политика действует, если недоступен датчик, использованный как динамический порог.
- Недоступный датчик присутствия означает «дома»; недоступные границы ночи означают «не ночь».
- Ошибка расчёта или команды логируется и не роняет Home Assistant, предыдущий план сохраняется.
- Профили с ошибками пропускаются при загрузке с сообщением в лог; если ни одного валидного вентилятора не осталось, настройка интеграции завершается ошибкой (`ConfigEntryError`), а не тихим запуском без вентиляторов.
- Вентилятор «только чтение» никогда не получает команд; при его недоступности он просто исключается из баланса, как и любой другой.
- Вотчдог зависших вентиляторов и срочная коррекция давления (см. выше) гарантируют, что значимое расхождение между фактическим и целевым уровнем не длится бесконтрольно долго.

## Мастер-сущность

`fan.vav_balancer` (одна на интеграцию):

- **on** — контроллер отправляет команды на вентиляторы;
- **off** — только расчёт (контур 1), контур 2 ничего не отправляет. Состояние восстанавливается после перезапуска.

Основные атрибуты: `target_intake_m3h`, `target_exhaust_m3h`, `requested_exhaust_m3h`, `target_delta_m3h`, `actual_intake_m3h`, `actual_exhaust_m3h`, `actual_delta_m3h`, `night_mode`, `home_mode`, `pressure_tolerance_m3h`, `max_correction_seconds`, `intake_targets`, `exhaust_targets` (уровень, расход, спрос, потолок, `read_only`, `stuck_seconds` **и список правил с их текущими порогами** по каждому вентилятору), `notes`, `last_reason`, `last_calculation`, `last_execution`, `last_commands`.

## Сущности для dashboard

Помимо мастер-сущности интеграция создаёт отдельные сенсоры — это даёт графики истории и статистики средствами самого Home Assistant, без сторонних карточек.

**Глобальные сенсоры (м³/ч), каждый с `device_class: volume_flow_rate` и `state_class: measurement`:**

| Сенсор | Значение |
|---|---|
| `sensor.vav_balancer_target_intake_flow` | Целевой суммарный приток |
| `sensor.vav_balancer_actual_intake_flow` | Фактический суммарный приток |
| `sensor.vav_balancer_target_exhaust_flow` | Целевая суммарная вытяжка |
| `sensor.vav_balancer_actual_exhaust_flow` | Фактическая суммарная вытяжка |
| `sensor.vav_balancer_requested_exhaust_flow` | Запрошенная вытяжка до учёта положительного давления (по умолчанию отключён в реестре сущностей; категория — диагностика) |
| `sensor.vav_balancer_target_delta` | Целевая дельта приток-вытяжка |
| `sensor.vav_balancer_actual_delta` | Фактическая дельта приток-вытяжка |

**По каждому настроенному вентилятору** (имя сущности строится из его `object_id`, то есть из части после точки в `fan.xxx`):

- `sensor.vav_balancer_target_flow_<object_id>` — целевой расход, м³/ч. В атрибутах: `control`, `target_level`, `demand_level`, `ceiling`, `available`, `read_only`, `stuck_seconds` и `rules` — список правил этого вентилятора с полями `sensor`, `mode`, `threshold`, `threshold_source` (`fixed` или entity_id датчика-порога), `threshold_high`, `threshold_high_source`, `output`, `active`, `delay_seconds`, `hysteresis`, `pending` (сырое состояние ещё не подтверждено задержкой активации).
- `sensor.vav_balancer_actual_flow_<object_id>` — фактический расход, м³/ч, вычисленный из текущего состояния самого вентилятора.

Оба сенсора становятся `unavailable` (не «0» и не «unknown»), если для них нет осмысленного значения — например, до первого расчёта (целевой) или пока состояние самого вентилятора нечитаемо (фактический).

**Бинарные сенсоры** (категория — диагностика):

- `binary_sensor.vav_balancer_night_mode` — применяется ли сейчас ночной потолок;
- `binary_sensor.vav_balancer_home_mode` — учитывается ли «домашний» или «отсутствующий» минимум.

Точные `entity_id` зависят от того, как Home Assistant разрешит совпадения имён — проверьте их в **Инструменты разработчика → Состояния**, отфильтровав по `vav_balancer`.

### Пример дашборда

В комплекте есть `dashboard_example.yaml` — вид YAML для ручного режима Lovelace с графиком `history-graph` (цель/факт по притоку и вытяжке, дельта давления), карточкой `glance` для режимов и `markdown`-карточкой, которая через Jinja читает атрибут `rules` целевого сенсора и строит таблицу «датчик → порог → источник → выход → активно» для конкретного вентилятора. Перед использованием замените плейсхолдер `<object_id>` на реальные части `entity_id` ваших вентиляторов.

## Логирование и диагностика

Все сообщения на английском. Подробная трассировка (валидация конфигурации, каждая фаза балансировщика, каждый тик и команда):

```yaml
logger:
  default: warning
  logs:
    custom_components.vav_balancer: debug
```

Для разового снимка состояния (для отчёта об ошибке) используйте **Настройки → Устройства и службы → VAV Ventilation Balancer → Скачать диагностику** — файл содержит текущую сохранённую конфигурацию и полный расчётный срез контроллера (цели, фактические расходы, активные правила, предупреждения). Конфигурация не содержит учётных данных — только entity_id и числовые настройки.
